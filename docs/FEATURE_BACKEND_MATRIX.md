# Feature Backend Matrix

Per `route/component → API(s) → permission → service/business rule → database entities → loading/error/empty response → audit event`. This matrix is a required deliverable (see the implementation brief, section 1.3) and must have a row for every user-facing data/action feature.

Status column: **live** = fully implemented against real D1 tables and verified by build; **adapter** = served by the legacy `/api/*` compatibility routes against the pre-overhaul tables (`portal_content`, `submissions`, `media_assets`, `knowledge_entries`) pending frontend migration to `/api/v1/*`; **frontend-pending** = backend contract exists but the current frontend component does not call it yet.

## Known gaps and honest status (do not treat as complete)

These are explicitly **not** fully production-ready and are called out rather than silently omitted, per the brief's "no silently skipped feature" rule:

1. **R2 bucket not provisioned.** `.openai/hosting.json` has `"r2": null`. `server/storage/r2-storage.ts` throws a clear 503 (`"التخزين السحابي (R2) غير مُفعّل..."`) until an `R2Bucket` binding named `BUCKET` is attached and `.openai/hosting.json`'s `r2` key is set. All media-upload admin endpoints depend on this.
2. **No true presigned S3 upload URL.** Cloudflare R2's S3-compatible presigned URLs need `R2_S3_ACCESS_KEY_ID`/`R2_S3_SECRET_ACCESS_KEY` secrets, not available here. `POST /api/v1/admin/media/sign` instead returns a same-origin Worker URL (`PUT /api/v1/admin/media/upload/:objectKey`) that proxies bytes into R2 server-side. Functionally complete, but not a literal presigned URL — swap the implementation once S3 credentials exist, the response shape won't need to change.
3. **No Cloudflare Queues binding.** `queues: {producers: [], consumers: []}` in the generated Worker config. Notifications, search re-indexing, and assistant knowledge ingestion are durably recorded in a D1 `outbox_jobs` table and drained by `POST /api/v1/admin/jobs/drain` instead of a real queue consumer. This works but needs either a Cron Trigger (not configured in this project — no `wrangler.toml`/`[triggers]` block was present) or a human/admin action to call the drain endpoint periodically.
4. **No transactional email provider configured.** No `EMAIL_PROVIDER`/`EMAIL_API_KEY`/`EMAIL_FROM` secrets exist. `server/notifications/email-adapter.ts` logs a warning and returns `ok:false` instead of sending. Intake acknowledgements and event-registration confirmations are queued but will not actually deliver until a provider is wired.
5. **No Cloudflare Turnstile secret.** Public forms rely on honeypot + D1-backed IP rate limiting only; `TURNSTILE_SECRET_KEY` is declared in `cloudflare-env.d.ts` but no route currently verifies a Turnstile token because no site/secret key pair exists yet.
6. **No AI provider for the assistant.** The assistant answers from `knowledge_entries` keyword matches and published `content_entries` title matches only — this satisfies the brief's "never fabricate" requirement by construction, but is not semantic/LLM-backed. Wire `AI_PROVIDER_API_KEY` and extend `assistant-service.ts` to call a real provider while keeping retrieval scoped to the same approved-source set, if richer answers are wanted later.
7. **Frontend is not yet migrated to `/api/v1/*`.** Every existing component (`ContentBrowser`, `SubmitForm`, `ChatAssistant`, `MediaGallery`, `AdminDashboard`) still calls the legacy `/api/*` routes against the original tables. The new backend is additive and fully functional, but a second phase of frontend work is required to point these components at `/api/v1/*` and retire the adapters — this is explicitly a frontend task, not a backend gap.
8. **No automated test suite exists yet** (unit/integration/contract/E2E) — flagged in Task 11's summary; see `docs/OPERATIONS_RUNBOOK.md` for what was verified manually instead (migrations-from-empty, bootstrap script, full build).

### Additive gaps from the Membership / Issue Intelligence extension (spec §15)

9. **No public applicant file-upload endpoint.** `POST /api/v1/membership/applications` expects `profilePhotoAssetId` (and optional supporting-document asset IDs) to already reference a confirmed `storage_assets` row, but the only upload-sign/confirm flow built so far (`/api/v1/admin/media/*`) requires a staff session. A public applicant has no credentials yet. Add a public, Turnstile-gated, narrowly-scoped upload endpoint (distinct from the admin one, with tighter MIME/size limits) before `/membership/apply` can work end-to-end for a real applicant.
10. **No membership card image rendering.** `membership_cards.renderAssetId` and the card template's `layoutConfigJson` exist as data model, but nothing actually composites a template + member data into a rendered image/PDF asset. `getCurrentMembershipCard` returns a placeholder `renderAssetUrl` path. Implement a render job (likely in `server/jobs/handlers.ts`, producing a `storage_assets` row) before the card page can show a real image.
11. **No RSS/API poller for monitoring sources.** `monitoring_sources.sourceType` supports `rss`/`official_website`/`approved_api`, and the active-requires-legal-review gate is enforced, but there is no scheduled job that actually fetches from these sources — `POST /api/v1/admin/monitoring/ingestions` is manual-entry only. A real poller is future work; the manual path still satisfies "ingestion never publishes directly" today.
12. **No card-template preview-with-synthetic-data.** Spec §15.4 asks for template preview before activation; `admin/card-templates` only supports create/list, no preview rendering.
